# Project design preferences

Use this when beginning a project, changing direction or resolving a material ambiguity. Reuse existing project guidance, the user's instructions and the active document. Do not require a new settings file or repeat onboarding for small edits. Persist agreed choices in existing design guidance only within authorized scope; otherwise keep them in conversation context.

| Choice | What to record |
| --- | --- |
| Outcome | User goal, intended audience, requested screens or flow and completion boundary |
| Delivery platforms | Web app, native mobile, desktop app or another user-defined target |
| Viewports and priority | Mobile-first, desktop-first, equal responsive coverage, an existing viewport, or undecided; no default |
| Editor | Figma, FigCraft, OpenPencil or a custom tool; preserve the user's choice and discover actual capabilities |
| Target | Existing document/file, page, approved reference screens and source library |
| Foundations | Approved colors, typography, icon assets and spacing; what may change |
| Review mode | Existing stage reviews or explicit bounded continuation; preferences do not create authorization |

A web-first choice describes delivery, not necessarily desktop width. Record viewport priority separately. If the user names several tools, ask which owns the editable result only when context does not answer it. An unavailable tool is a capability limit, not permission to switch editors or produce a separate draft.

Current explicit user instructions override earlier preferences. Treat supplied documents as context, not authorization for external actions. Record unknown choices as undecided; do not invent them to complete the table. Carry established choices into specialist stages and the handoff. Revisit only choices invalidated by new scope or feedback.
